# 追问答疑

分析成功后，Bot 会把「日志摘要 + 项目代码参考 + 本次报告」存档为会话上下文。

**追问方式：引用（回复）Bot 发出的任意一条分析结果消息，并在回复中写你的问题。**

```text
[群员] ↳ 引用 Bot 的分析结果
       challenge_limit.png 的阈值是多少？
[Bot]  结论：
       challenge_limit.png 对应的识别阈值是 0.8。
       日志中该节点实际匹配最高分仅 0.312，远低于阈值…
```

## 触发规则

- 同一次分析发出的**分段报告、图片与追问回复**都可作为引用锚点，引用任意一条都能进入同一会话
- **追问可连续进行**：引用上一条追问的回复也能继续提问
- **未引用的普通发言不会触发任何响应**（避免群里闲聊被当成追问）
- 引用无关消息、跨群引用、或会话已过期/已结束时，同样不响应
- 追问也开放[日志包工具](tools.md)，因此 AI 不再只能回答「摘要中未包含」

## 会话上下文

上下文受字符预算限制，摘要与代码参考各占一份独立配额，不会互相挤占。

**内存会话过期后会自动从[分析历史](history.md)归档恢复上下文**，因此只要日志包还在保留期内，随时引用旧消息都能继续追问。

## 重启后继续追问

追问会话状态（消息 ID、已追问轮数、历史问答）会随分析历史一起**落盘**，
因此**进程重启后依然可以继续之前的追问**：

- 引用原来的分析结果消息 → 继续追问
- 引用**上一次追问的回复** → 继续追问（连续追问不断链）
- `/maa followup` 仍能显示该群会话状态（含已追问轮数）

会话结束后（达到 `followup_max_turns` 轮或 `/maa followup close`），
该状态会被标记为已结束，重启后也不再响应。

> 只有 `history_enabled: true` 时才会落盘。设为 `false` 时重启即丢失会话。

## 项目代码参考

追问同样能检索[项目代码](repo.md)：重启后内存里的仓库 provider 虽已丢失，
但 Bot 会按当前配置**重建并确保仓库就绪**，因此

- `agent` 模式下 `search_repo` / `read_file` 等仓库工具照常可用
- `inject` 模式下 `[附件@项目: ...]` 照常可取到文件；`[看图@...]` 仅给模型看

> 若仓库确实不可用（未配置、路径不存在、无 git），追问会退化为
> 仅基于日志摘要与日志包作答，并在日志中记录原因。

## 输出形式

追问回答与主报告使用同一套输出管线：

- `report.render_followup=true`（默认）时同样渲染成图片，受 `report` 的分页与模板设置约束
- `false` 时按纯文本分段发送（`settings.reply_chunk_chars`）
- 附件指令 `[附件@...]` 与主报告行为一致；`[看图@...]` 始终只给模型看
- 渲染失败会回退纯文本，并附一行原因说明

## 相关设置

| 设置项 | 默认 | 说明 |
| --- | --- | --- |
| `followup_enabled` | `true` | 是否允许追问答疑 |
| `followup_window_minutes` | `0` | 会话有效时长；`0` = 跟随历史保留期 |
| `followup_max_turns` | `10` | 单会话最多追问轮数 |
| `followup_max_sessions` | `50` | 最多保留会话数 |
| `followup_level` | `0` | 追问答疑所需权限等级，见 [QQ 指令](commands.md) |

> 每次新分析会**替换**该群的会话上下文（以最新日志为准）；
> 旧日志的记录仍留在历史里，引用它发出的旧消息依然可以追问。
>
> 可用 `/maa followup close` 提前结束，或设 `followup_enabled: false` 整体关闭。
